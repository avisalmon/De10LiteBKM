14 · Fill the 64 MB SDRAM from the PC over USB

The DE10-Lite's only link to a PC is its USB-Blaster: a JTAG cable. This example streams a file through it straight into the SDRAM, proves the load with a CRC the board computes itself, and reads the memory back. Three routes were measured until the fastest one hit the cable's own limit: 64 MB in 112 s (583 KB/s), proven in 9.5 s, read back in 138 s. The same path will carry the parameters of an LLM later.

Verified on the board 2026-10-27: 64 MB written, CRC-checked and read back, 0 errors, twice Quartus Prime Lite 17.1 No shield needed Skill: load-sdram-usb

  • 583 KB/s is the cable, not the software. The on-board USB-Blaster is an FTDI FT245 USB FIFO in front of a small CPLD that turns bytes into JTAG clocks; the CPLD takes about 41 cycles of its 24 MHz clock per byte, so ~585 KB/s is its ceiling. Three different drivers converge on it: the JTAG server leaves 6 % on the table (its own packetizing), the direct driver none. Bigger blocks, a shorter latency timer, several blocks in flight: all measured, none moves it.
  • Reads are slower because the bus is full-speed USB (12 Mb/s, shared by both directions): a read sends every byte out as a command and gets a byte back, and the two streams together come near the bus's bulk budget, so reads land between 470 and 540 KB/s depending on what else the host's USB controller is doing. Writes are steady to 0.1 %.
  • The SDRAM side is never the limit: the loader writes a word every ~10 clocks at 50 MHz (10 MB/s, 17 times the cable), and the board's CRC engine reads at 6.7 MB/s. Faster loading needs a faster link, not a faster FPGA: a USB 2.0 high-speed FIFO chip (FT232H / FT2232H, 20–30 MB/s) on the GPIO header is the next step, when a design needs it.
  • Resources: 2,556 logic elements (5 %), 0 memory bits (the loader's FIFO is 16 words of registers), one PLL; the design runs at 50 MHz (Fmax 96 MHz), no negative slack. The virtual JTAG side runs on the cable's 6 MHz TCK.

How the loader works (lib/rtl/sdram_loader.sv)

A virtual JTAG node (Altera's sld_virtual_jtag) with a 4-bit instruction register. Every data register shifts LSB first; 16 bits make one SDRAM word (the first file byte is the low byte), and one DR scan can be as long as you like: the PC shifts 4 MB per scan, the words cross from the cable's clock to the 50 MHz clock through a small FIFO and go to consecutive addresses as they arrive. Nothing is buffered on the FPGA: a 64 MB load is one stream.

VIRDRDoes
1 WADDR64 inWord address of the next write; clears the write count, CRC and flags
2 WRITEn × 16 inThe data; the address advances by itself, also across scans
3 RADDR64 inWord address where reading (re)starts
4 READn × 16 outThe data back, prefetched so the cable never waits
5 STATUS320 outMagic SDLD, flags, words written and their CRC32, words received, words sent, the CHECK result, two words from the design
6 CHECK64 inStart word and count: the board reads that range and CRC32s it (6.7 MB/s), result in STATUS

A load is proven twice without trusting the cable: the CRC32 of what arrived (counted as it is written) and the CRC32 of what the SDRAM holds afterwards (CHECK); both must equal zlib.crc32 of the file. verify reads everything back over the cable too and compares every byte: the 64 MB runs above did all three.

Two routes, one command

  • direct (scripts/usb_blaster.py): Python drives the cable through the FTDI D2XX driver that Quartus installs (drivers/usb-blaster/x64/usbblstr64.dll), speaking the USB-Blaster's own byte protocol (bit-bang bytes and 63-byte shift blocks). No JTAG server, no admin rights, Windows only. While a script holds the cable, Quartus tools cannot have it, and the other way round (CableBusy: close de10.py log / nios2-terminal first).
  • quartus (scripts/sdram_load.tcl under quartus_stp): the portable route, one tool process per session fed commands over its stdin. 6 % slower writing, a third slower reading.
  • --via auto (the default) takes the direct route and falls back to quartus when the cable's DLL is missing. Both routes speak the same protocol to the same loader; bench reports the route it used.

Things learned (each cost real time)

  1. The JTAG server is the cap, not the cable. Every Quartus tool reaches the cable through it, and a long virtual JTAG scan tops out at ~525–547 KB/s written, ~300–355 KB/s read, whatever the scan length. The cable itself does 583 KB/s.
  2. quartus_stp holds its stdout back until it exits when stdout is a pipe (Tcl's flush does not help), while it reads stdin promptly. Live answers go through a file opened with -buffering none, which Python tails.
  3. Scans without a captured value are only queued (-no_captured_dr_value): a write timed on the Tcl side must end with a captured scan (the STATUS read does it), or the clock stops before the data has left.
  4. The cable protocol has no framing. If a byte is ever lost or misread, data bytes become commands; a random command stream can fill the cable's answer FIFO until it stalls, or even pulse the FPGA's nCONFIG (it reloads its flash: seen once, in an unguarded sweep, never again). The driver now checks that nothing unasked-for arrived after every 64 KB block and at every scan end, resets the TAP and raises; the CRC on every load catches whatever a check could miss.
  5. TDO is sampled on the TCK-high byte. Reading bit 0 of the answer to the TCK-low byte gives the previous bit.
  6. Drain by queue status, single-threaded. A reader thread beside the writer deadlocks the D2XX driver; its receive queue holds 64 KB, so never leave more than one 64 KB block unread.
  7. One board, two chats. Another session was using the same board; a lock file (%LOCALAPPDATA%\de10lite\board.lock: who, what, since when) and a "board free" message kept them apart.

Use it in your own design

Put sdram_loader on the master port of sdram_ctrl (--lib pll loader, and src/extra.qsf from here for the SDRAM pins); the design uses the SDRAM itself while busy is low. Report two words of your own in STATUS through user0, user1. Then sdram_load.py load fills the memory before your logic starts: parameters, tables, pictures.
