12 · DSP multipliers vs logic

The MAX 10 has hardware multipliers. This example runs the same multiply-accumulate engine twice, once in them and once in ordinary logic, checks both against Python, and measures what each costs.

The Python reference (sim/mac_reference.py) gives 01E17200A928 too. The 10M50 has 288 multiplier elements (144 of 18 × 18), so a design can have up to 144 multiplies running every clock for free. Fmax moves a few MHz between builds; the ranges are from the builds of this example.

How to choose where a multiply goes

(* multstyle = "dsp" *)                       // or "logic"
module mult18_dsp (input signed [17:0] a, input signed [17:0] b, output signed [35:0] p);
  assign p = a * b;
endmodule
  • By default Quartus puts every * it can into the embedded multipliers. Most of the time that is what you want.
  • Put the multstyle attribute on a module. On a wire inside a generate block Quartus 17.1 ignored it and both engines ended up in DSP blocks: check the fitter's per-entity report ("DSP Elements" column) to see where a multiply really went.
  • Each embedded multiplier is 18 × 18 (or two 9 × 9). Wider products use several, plus adders in logic.
  • Register the product before adding it (the engine does: p <= a * b; acc <= acc + p;): one multiply-add per clock and an easy timing path.

Things learned building it

  • A result that crosses clocks after a "done" handshake still shows up as a timing failure (here −0.24 ns from 75 MHz into 50 MHz). It is safe because the value is not changing when it is read; say so in the .sdc: set_false_path -from [get_registers {*mac:*|acc[*] *mac:*|cycles[*]}] -to [get_clocks clk50] (src/timing.sdc).
  • Checking against a reference model (Python) catches everything: off-by-one in the pipeline, wrong signs, wrong widths.
