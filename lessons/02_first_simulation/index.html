Lesson 2

Your first simulation

Today you test a design on the computer, before it ever reaches the chip. A testbench tries every case, a waveform shows you the moment it goes wrong, you fix it in VS Code, and then you make the test itself better.

The design: a door alarm

Somebody wrote it in a hurry. It compiles. It even works when you try it on the board with the switches you happen to flip. But it has a bug, and the simulator will find it in one second.

About 40 minutes. You work in VS Code; the chat runs the simulator and the board for you and checks every step.

Lesson 2 · the idea

Why test on the computer first?

On the board you see what you try

  • Only the switch positions you happen to flip.
  • Only the outputs you can see (an LED, a digit).
  • Every change costs a compile and a program.

In the simulator you see everything

  • Every input combination, in order, automatically.
  • Every signal, at every moment, as a waveform.
  • A program checks the answers and says PASS or FAIL.
Engineers' ruleSimulate first, then build. A bug found in simulation costs seconds; on a chip in a product it can cost a recall.

Lesson 2 · the design

Read the design

The chat put the lesson's files into my_designs\lessons\02_first_simulation\alarm. Open src\door_alarm.sv in VS Code:

module door_alarm ( input logic armed, input logic door, input logic window, output logic alarm ); assign alarm = armed & door | window; endmodule

& is AND, | is OR. The assign line says how the output is computed from the inputs.

Does it look right to you? Keep your answer; in a few minutes ModelSim will tell you.

The foldersrc\ holds what goes into the chip (the design). sim\ holds what only the simulator runs (the testbench). Every project in this course uses these two folders.
Lesson 2 · the testbench

A testbench: a module that tests a module

Open sim\tb_door_alarm.sv. The important parts:

// 1. a copy of the design, with wires plugged into it door_alarm dut (.armed(armed), .door(door), .window(window), .alarm(alarm)); // 2. one test case: set the inputs, wait 10 ns, compare with what we expect task check(input logic a, input logic d, input logic w, input logic expected); armed = a; door = d; window = w; #10; if (alarm === expected) $display("ok ..."); else begin $display("WRONG ..."); errors = errors + 1; end endtask // 3. the list of test cases, run once from the start initial begin check(0, 0, 0, 0); // off, all closed: quiet check(0, 0, 1, 0); // off, window open: quiet ... six cases in all ... if (errors == 0) $display("PASS ..."); else $display("FAIL ..."); $stop; end

#10 means "wait 10 nanoseconds" (simulated time, not real time). $display prints a line. $stop ends the run (it pauses, so the waveform stays open for you to read).

Lesson 2 · step 1

Run the test

In the chat, say run my test. The chat runs the simulator for you:

python scripts/sim.py my_designs/lessons/02_first_simulation/alarm/sim/tb_door_alarm.sv --modelsim ok armed=0 door=0 window=0 -> alarm=0 WRONG armed=0 door=0 window=1 -> alarm=1, expected 0 ok armed=0 door=1 window=0 -> alarm=0 ok armed=1 door=0 window=0 -> alarm=0 ok armed=1 door=0 window=1 -> alarm=1 ok armed=1 door=1 window=0 -> alarm=1 FAIL: 1 test case(s) wrong

The testbench found a bug. With the system off and only the window open, the alarm sounds. Your neighbours will not be happy.

Behind that command is ModelSim, the simulator that came with Quartus. It compiles your two files and runs the testbench; you never have to open it.

Lesson 2 · the bug

Why: AND goes before OR

In Verilog, like in math, some operators go first. & (AND) goes before | (OR), just as × goes before +:

2 × 3 + 4 is (2 × 3) + 4 = 10 armed & door | window is (armed & door) | window

So the window alone sets off the alarm, armed or not. The rule needs the OR done first.

How would you make the OR happen first? (The same way you would in math.)

Lesson 2 · how it works

The loop you will use in every lesson

  1. Write the design and its testbench in VS Code.
  2. Simulate: the chat runs the testbench. PASS, or a WRONG line and a waveform.
  3. Build and load: the chat compiles the design for the chip and loads it into the board.
  4. Try it on the board with your own hands.

How does the chat know which files to simulate? The testbench says so, in one comment line at its top:

// sim-sources: ../src/door_alarm.sv

And which pins? The board's own names: a port called SW is the switches, LEDR the red LEDs, HEX0 a digit. Use those names in the top module and the chat's build finds every pin.

Lesson 2 · the twist

PASS. But is the test good enough?

The chat has two more door alarms, each with a different hidden mistake. Run against them, your testbench says... PASS. Both times.

A testbench only checks the cases in its list. A mistake that hides in a case nobody wrote down goes straight through.

A PASS is only as good as the test cases behind it.

Your job: compare the testbench's list of check(...) lines with the truth table on slide 3. Which rows are not tested yet?

HintCount them: the table has 8 rows, the list has 6 lines.
Lesson 2 · step 6 · make it yours

Add the two missing test cases

Where the testbench says // (two more cases go here), add two lines that follow the same pattern:

check(armed, door, window, expected alarm);

Take the inputs and the expected alarm from the truth table. Save, say run my test again, then check my testbench: the chat runs it on your design, on a right one, and on the two wrong ones.

With all 8 cases: the waveform runs to 80 ns and errors stays 0.

Lesson 2 · step 7

Now prove it on the board

Say put it on the board. The chat compiles alarm_top (about 30 seconds) and loads it. In src\alarm_top.sv the switches and LEDs carry the board's names, SW and LEDR:

SwitchMeans
SW2armed (up = on)
SW1door open
SW0window open
LEDR0the alarm
  1. All three down: LEDR0 off.
  2. SW0 up (window), SW2 down (off): LEDR0 stays off. This was the bug.
  3. SW2 up too: LEDR0 on.
  4. Try a few more and compare with the truth table.

Tell the chat what you saw.

The board agrees with the simulation, because the simulation already tried every case. That is the whole point.

The end of lesson 2

Lesson 2 done!You found a bug before the chip did, and made the test itself better.

What you learned

  • A testbench is a module that drives your design's inputs and checks its outputs; only the simulator runs it.
  • The loop: write in VS Code, simulate (PASS or a WRONG line and a waveform), build and load, try it on the board.
  • Operators have an order: & before |. Parentheses say what you mean.
  • A PASS is only as good as the test cases: cover every case that matters.
