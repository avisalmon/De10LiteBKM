Accelerometer 3D cube: user guide

From the repo to the cube on your board, and everything you can do with it afterwards. Every command runs from the repo's root folder in the env virtualenv; the chat does them for you if you ask.

What you need

  • A DE10-Lite with the LCD / game-pad shield on its Arduino header. The sensor is on the DE10-Lite itself (the ADXL345 next to the Arduino header); nothing is wired. The shield is only the screen: without it the numbers still come on the 7-segment digits, the LEDs and the USB report.
  • Quartus Prime Lite 17.1 installed as in stage 1 of the BKM (python scripts/doctor.py shows no FAIL).
  • The repo cloned, env created (setup-my-computer does this), the board on the USB cable.

Build and load it

The sources are in the repo; one build makes the bitstream (the repo keeps none, they are 3 MB each):

python scripts/de10.py build   projects/accel_cube   # about 3 min; ends with the resource summary
python scripts/de10.py program projects/accel_cube   # over the USB-Blaster; lasts until power-off

From the archive instead (for example in the Quartus GUI): Project → Restore Archived Project → accel_cube.qar, then Processing → Start Compilation, then Tools → Programmer with output_files/accel_cube.sof. The archive holds the sources, the settings and the model.

What you should see right after loading, with the board lying flat on the table: on the left of the screen a cube on a blue sky, its blue face on top, seen from a little above and 30° to the side; on the right the panel: ADXL345 ID E5, then X, Y and Z near +0.000, +0.000, +1.000 G with a short bar next to Z, MAG and PEAK near 1.0, PITCH and ROLL near 0.0, the word LIVE in green, and at the bottom the three axes with a white arrow pointing up: the acceleration the board feels, which at rest is 1 g upwards. The 7-segment digits show L 1.000, one LED in the middle of the row is lit. Tilt the board: the cube tilts with it, the arrow follows, the numbers and the bars move, the lit LED slides along the row like the bubble of a spirit level.

Use it

ControlDoes
Tilt the boardthe cube turns with it, as if it were glued to the board: pitch (nose up and down) and roll (one side up). Turning the board flat on the table changes nothing: an accelerometer cannot see a turn about gravity, so there is no yaw.
Shake or tap itthe arrow, the bars and the X Y Z numbers jump (they show the latest sample); the cube hardly moves (it follows the filtered gravity). MAG is the size of the live acceleration, PEAK the largest since the last restart.
KEY1calibrate: take the current reading as "flat", with the board lying still and level. The numbers go to 0, 0, +1.000, the cube stands straight; the mode row says LIVE CAL and the digits C. The offsets are kept until power-off or u over USB.
KEY0restart the peak (PEAK starts again from the current MAG) and clear the status LED on the shield
7-segmentthe mode letter on the left (L live, C calibrated, a digit in a test preset), then |a| in g as d.ddd
LEDR0..9a bubble level along the board's x axis: the lit LED slides with the tilt. Every second LED lit (1010101010, LEDR9, 7, 5, 3, 1) means the sensor did not answer with its ID: see the trouble table.
Status LED (shield)lit when the per-frame math once missed its deadline. It never did in the simulation (the engine needs under 4 % of the time it has); if it lights, KEY0 clears it and the chat wants to know.

Colours: the faces are +X red, −X cyan, +Y green, −Y magenta, +Z blue (the top when the board is flat), −Z yellow. The arrow is drawn over three axes: x red, y green, z blue, 80 px each; 1 g is 64 px of arrow, with a grey shadow on the x-y plane and a dashed drop line so its height is readable. The bars are ±1 g wide between the grey ticks.

Test over USB

The design listens on the JTAG UART, the same link the BKM uses for logs. Each letter is one command (upper case works too):

python scripts/de10.py send 3 1          # test preset 3 (upside down); 0..7 are the eight presets
python scripts/de10.py send l 1          # back to the live sensor
python scripts/de10.py send c 1          # calibrate (as KEY1);  u forgets it
python scripts/de10.py send s 1          # spin the view slowly on / off (0.5 degree a frame)
python scripts/de10.py send k 1          # restart the peak (as KEY0)
python scripts/de10.py send r 2          # the report line: the numbers of the panel in one line
python scripts/de10.py send "?" 1        # the debug link's status line (keys, switches, frames)
python scripts/de10.py screen logs/x.png # the screen as the board shows it, 320 x 240 (about 6 s)

The report line looks like this (one line of 114 characters; AQ is the live vector in counts, 4096 = 1 g; this one is the simulation's, a calibrated board given a 2 g shake):

AQ -03200 +04800 +05696 X-0.781 Y+1.172 Z+1.391 MAG 1.979 PEAK 1.979
PITCH  +5.3 ROLL  +7.9 ID E5 LIVE CAL

The eight presets are the design's self-test: in a preset the sensor is ignored and both vectors are a fixed value, so the screen must match the model's picture to the pixel. The model draws it on the PC and compares:

python scripts/de10.py send 6 1
python scripts/de10.py screen logs/test6.png
python projects/accel_cube/assets/model.py compare seq:6 logs/test6.txt logs/diff6.png
# -> "0 of 76800 pixels differ"; a diff.png marks any that do

Give compare the .txt that screen writes next to the picture (the raw capture), not the .png. seq:6 means "preset 6 after presets 0..5", which is what the board shows when you step through them in order; a bare 6 is the preset on its own, straight after power-up. Presets 0..3, 5 and 6 give the same picture either way; 4 and 7 hold an angle from the frame before, so for them the two differ. This is how the eight presets were checked on the board, 0 of 76,800 pixels different each, and how you can check a change of your own without taking the board apart.

Keep it after power-off

Loading with program lasts until the power goes; to make the cube the design the board starts with:

python scripts/de10.py flash projects/accel_cube     # writes and verifies the .pof, about 15 s

It replaces whatever was in the flash before (the chat asks first). Loading other designs with program afterwards does not touch it; the cube returns at the next power-up. The library's flash-design skill and example 13 explain the .pof. The calibration offsets are not kept: press KEY1 again after a power-up.

Run the simulation

Two testbenches, one fast and one complete. Run the fast one after every change to the math:

python scripts/sim.py projects/accel_cube/sim/tb_cube_math.sv   # 1 s: engine numbers, 18 frames
python scripts/sim.py projects/accel_cube/sim/tb_accel_cube.sv  # 20 min: 13 frames, pixel by pixel

tb_cube_math runs the per-frame engine alone on the eight presets and ten more cases (yaws the presets cannot reach, the CORDIC's ±90° and ±180° corners, a peak kept across frames, two frames where the steady and the live vectors differ) and compares every number it produces (angles, matrix, corners, face colours, text digits, arrow points) with sim/math_expected.txt, which model.py dump wrote. A mismatch names the frame and the number. It also writes sim/math_dump.txt; python projects/accel_cube/assets/model.py dumpcmp projects/accel_cube/sim/math_dump.txt shows the two side by side.

tb_accel_cube drives the whole core with the real VGA timing, steps through the presets over the "USB" letters, then feeds 120 sensor samples through the filter, calibrates with KEY1, reads the report line, forgets the calibration and spins the view. Every frame is captured the way the board's screen capture is (every 2nd pixel and line), written next to the testbench as frame_0.ppm .. frame_7.ppm, frame_live.ppm, frame_cal.ppm, frame_calb.ppm, frame_u.ppm, frame_spin.ppm, hashed and compared with the model's hash. Open the pictures with any image viewer, or convert them with Pillow (Image.open("x.ppm").save("x.png")). On a mismatch, see where:

python projects/accel_cube/assets/model.py compare seq:3 projects/accel_cube/sim/frame_3.ppm d.png

The model has its own check against plain floating-point math, independent of any Verilog:

python projects/accel_cube/assets/model.py selftest           # angles, projection, visibility, text
python projects/accel_cube/assets/model.py render 5 cube5.png    # preset 5 as the board draws it
python projects/accel_cube/assets/model.py render 300,-200,900 x.png   # or any vector in mg

Both testbenches use Icarus (--gui opens the waveform in GTKWave). The top level with the PLL and the sensor is not simulated: the sensor reader is the library's, proven in example 07, and the board compare above covers the rest.

Change it

You wantWhere
the cube tilts the wrong way when you tilt the boardthe HEADING parameter of cube_core in src/accel_cube_top.sv: 0, 90, 180 or 270, which way the board's +x points on the screen. Rebuild (nothing in the model or the tests depends on it).
other test presetsPRESETS in assets/model.py and the matching table in src/cube_core.sv; then python projects/accel_cube/assets/model.py dump > projects/accel_cube/sim/math_expected.txt (from the chat or cmd: PowerShell's > writes UTF-16, which the testbench cannot read), hashes into sim/tb_accel_cube.sv, run both testbenches
other colours, a bigger cube, the panel elsewherethe constants at the top of assets/model.py (CX, CY, S_PX, D_PX, FACES, ROW_COLOR...) and the same numbers in src/cube_math.sv and src/cube_draw.sv: the layout and the colours are written in both by hand; the derived ones (sines, the light, the widget's projection and axes) come from python projects/accel_cube/assets/model.py constants, which prints them as Verilog localparams to paste. Then regenerate math_expected.txt and the hashes and run the testbenches. The model and the RTL must always agree: that is the whole test.
a calmer or a livelier cubethe filter in src/cube_core.sv: ex8 = ex >>> 3 moves the average 1/8 of the way to each new sample (100 Hz, so about 80 ms to settle); >>> 4 is twice as calm, >>> 2 twice as quick. The model's ema_live has the same >> 3: change both, then the ema: cases and the live frames of the long testbench still match.
a faster spin, another default viewSPIN_STEP (0.5° a frame) and VIEW_YAW (30°) in assets/model.py and src/cube_core.sv; the camera elevation SE, CE (30°) in the model, then constants
yaw, a compassnot possible with this sensor: turning about gravity leaves the measured vector unchanged. It needs a magnetometer or a gyroscope on the GPIO header (3.3 V only; unplug the board first).
the orientation of the sensor on another boardthe sensor frame is turned into the board frame in cube_core (head_x, head_y), nowhere else

After any change: tb_cube_math (1 s), then build (timing OK), program, and compare one preset on the board. The long testbench is for the end of the day.
