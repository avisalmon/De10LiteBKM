FFT Lab

A small signal lab on one screen. A wave generator makes six shapes at a frequency you set with the shield's wheel; the top half of the screen is a scope, the bottom half shows the spectrum twice: our own 256-point FFT on the left, Altera's FFT IP on the right. Both get the same samples in the same clocks, and each shows how long it took: 6,145 clocks for ours, 1,637 for the IP. Every pixel was checked against a bit-exact Python model, in simulation and on the board.

The Altera FFT IP runs in evaluation mode in Quartus Lite (free, no license): the build writes only a time-limited fft_lab_time_limited.sof, which keeps running while the programmer stays connected (without it, one hour by Intel's guide; we saw 32 minutes and stopped watching), and no .pof, so this design cannot be flashed. The user guide has every command.

In plain words: everything the lab does runs on one clock, pll clk[0] at 25 MHz (the pixel clock): the generator, both FFTs, the bars, the screen and the USB link. It could run at 38 MHz. The game pad and its debouncer run at 50 MHz, the LCD's driver at 100 MHz, the ADC on its own 10 MHz PLL, and altera_reserved_tck is the USB-Blaster's JTAG clock. Every setup slack is 2.85 ns or more; the worst slack of all, +0.101 ns, comes from the other checks (hold, recovery, removal), and it is met. The biggest block is Altera's FFT IP: 1,734 logic elements and 1,425 registers, against 398 and 189 for ours (fft_r2). The frame buffer in debug_link (114 M9K blocks, 921,600 bits) is there only so the PC can read the screen back for the tests; without it the lab needs 23 M9K blocks and 113,992 bits.

What you will see

All four pictures were read back from the board over USB (scripts/de10.py screen). Turn the wheel and the frequency follows, in steps of 12.5 Hz up to 12,787.5 Hz, on the screen and on the 7-segment display. Left and Right pick the shape (sine, square, triangle, saw, spikes, noise), A turns the Hann window on and off, B switches the bars between dB and linear, Start freezes the frame, Select plays the frequency on the buzzer, and KEY0 goes back to a 1 kHz sine. The top lines of the screen say what is set; under each spectrum is how long it took. The same settings can be sent as letters over USB, which is how the tests drive it.

The tutorial goes through it one experiment at a time: what to do, what you should see (a board picture checked against the model), and the DSP behind it: bins, leakage, windows, harmonics, combs, noise, aliasing, and how the two FFTs differ.

Block diagram

Two clock domains meet once. The game pad lives on the 50 MHz side, where the ADC is read: its 8 buttons are debounced there (5 ms steady) and each crosses to 25 MHz through two flip-flops. The wheel crosses as a raw 12-bit number, and lab_ctrl takes a value only when two samples in a row agree, so a number caught half-changed is never used. The keys are synchronised the same way. Everything after that runs on the 25 MHz pixel clock, so the FFTs write straight into the drawing memories and the screen reads them in the same clock: no more crossings. The engine is a block of its own because it works only in the vertical blanking, once a frame, while lab_draw works on every pixel all the time. The block names are the files in src/; the architecture spec has their ports.

How it flows

  1. The frame tick is the start of vertical sync, 59.5 times a second. Unless hold is on, the engine takes the live settings and starts a frame.
  2. wave_gen makes 256 samples of the shape at the frequency step (times the Hann table when the window is on). Each sample goes to the Altera IP and, in the same clock, to our fft_r2. A sample moves only when the IP is ready, so both see the same input at the same time. Clock 1 is the first sample moving.
  3. Each FFT's timer stops at its last output: 1,637 clocks for the IP, which streams, and 6,145 for ours: 256 to load, 5,120 for 8 stages × 128 butterflies × 5 clocks, 768 to read out, and 1.
  4. Every output goes through mag_px: re² + im², then a table turns it into a bar height (1 pixel per dB, or linear) for bins 0 to 127. The tallest bar of each side is kept.
  5. The scope memory gets the 256 samples as vertical spans (sample n to sample n + 1), so the trace has no gaps.
  6. When both FFTs are done, the results are published: the bars, the trace, the times and the peaks change together. If the IP does not answer within 20,000 clocks (0.8 ms), it is marked as not running: its panel says IP IS NOT RUNNING, the shield's LED lights, and the frames go on with our FFT alone.
  7. lab_digits turns 12 numbers into decimal digits, one at a time; lab_draw paints every pixel from the memories and the text. The report line goes out over USB when asked (R).
  8. All of this fits in the vertical blanking: 35 lines × 800 = 28,000 clocks. The slowest frame in simulation took 20,253 clocks (a silent IP, until the watchdog gives up).

Numbers

The figures that are not resources (those are at the top).

SpeedOurs 6,145 clocks = 245.8 µs at 25 MHz. The IP 1,637 clocks = 65.48 µs, 3.75 times faster. Counted in the design from the first sample in to the last result out, the same for both, and shown on the screen.
PrecisionOn the same 16-bit input the IP keeps 66.9 dB signal to noise, ours 56.3 dB: ours halves the numbers at every stage to stay in 16 bits; the IP's block floating point scales only when it must. Measured in examples/11.
FrameA new spectrum every frame: 59.5 per second (800 × 525 clocks of 25 MHz). Work per frame: 28,000 clocks allowed, 20,253 at most.
Signal256 samples of 16 bits at three quarters of full scale (24,576). Frequency = step × 12.5 Hz, step 0 to 1023, for a sample rate of 25.6 kHz: one bin is 100 Hz. (The samples are computed, so the rate is a label: they are made as fast as the FFTs take them.)
Bars128 per FFT (bins 0 to 127), 0 to 90 pixels: 1 pixel per dB (10 dB a division), or linear with 90 pixels at full scale.
Build4 min 19 s. 2 critical warnings, the board's own layout (the VGA sync pins sit next to the ADC pins). 112 warnings, none a mistake: 36 about unused memory bits removed, almost all in the ADC core; 21 width or unused-signal notes, 8 of them in fft_r2 (kept identical to examples/11) and the rest in library cores; 12 ROM nets with no driver (an inferred ROM's unused write side); 16 timing constraints of the JTAG UART core that match nothing here; 6 notices about the evaluation IP; 4 pins held constant on purpose; 17 other tool notes (the processor count, the ADC's PLL, the unused end of the LCD's command ROM).
Code1,264 lines of SystemVerilog in 10 files (our FFT: 139). Tests: 796 lines of SystemVerilog and 959 of Python. The IP generator script: 51 lines.

How it was tested

Without the board: a bit-exact model and five testbenches

sim/lab_model.py is the whole lab in Python, bit for bit: the generator, our FFT's rounding, the bar heights, the screen picture and the report line. It also writes the tables in assets/. Against it:

  • tb_wave_gen: every sample of every shape, with random stalls. tb_fft_r2: every output bit-exact, and the clock count. tb_mag: every (re, im) to its bar height.
  • The real IP: sim/record_ip.py runs Altera's simulation model of the IP in ModelSim on 13 frames, checks every number against the model and records them in sim/ip_vectors.hex. Icarus cannot run the IP, so the system testbench replays the recording (sim/fft256_replay.sv).
  • tb_fft_lab, run by sim/check_tb.py: the whole core for 27 frames, 62 checks. 12 screen pictures compared pixel by pixel and 7 report lines compared with the model; the IP silent (the watchdog, IP IS NOT RUNNING) and the IP answering zeros; hold, the wheel and the sound.

Result: PASS, every check. The system test takes about 4 minutes in Icarus. tests/test_fft_lab.py runs all of it and checks that the tables and test vectors are the model's.

On the board, over USB

sim/board_check.py drives the running board with USB letters through 17 settings. For each it reads the report line, captures the screen and compares both with the model: every one of the 76,800 pixels and every number. 13 of the settings are the ones recorded from the IP in ModelSim, so the IP's panel is compared too; for the other 4 the IP's panel is left out, and for noise (new every frame) only the clocks and IP_OK are checked. Result: PASS, 17/17, 0 pixels different, in 225 s.

Only a person can check

The wheel, the joystick, the buttons and the keys by hand (the tests send the same settings as letters, and the simulation drives the wheel's input), the buzzer (the AI has no microphone), and the LEDs and 7-segment by eye. These are open; see the status below.
